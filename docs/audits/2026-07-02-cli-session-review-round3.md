### 4. [MEDIUM] onMouse's click-to-select bounds check uses `idx < len(m.view)` instead of the actually-rendered range, so a click below the last visible table row can silently select an off-screen row.
- **File:** `ui/ui.go` line 268 (finder: ui-render-math)
- **Verdict:** CONFIRMED
- **Failure scenario:** Whenever the terminal is short relative to the number of matching rows (e.g. height=15 gives listHeight()=3 visible rows, but the filtered view has 20 rows): clicking at screen Y=7 (which is below the 3 rendered rows, e.g. in blank space between the table and the detail pane) computes idx = offset(0) + (7-2) = 5, and since 5 < len(view)=20 the click is accepted and cursor jumps to row 5 -- a row that was never drawn at that Y. Empirically confirmed with a driver test against the real package: 'listHeight=3, total view rows=20; clicked Y=7 -> cursor=5 (visible rows were only Y=2..4)'. The fix is to bound idx by min(m.offset+m.listHeight(), len(m.view)) (the same `end` tableView() computes), not just len(m.view). Not a panic -- clamp() keeps cursor in bounds -- but it is a real, easily reachable off-by-range selection bug: 'x'/'s' immediately after such a click opens a stop-confirmation dialog for the wrong, invisible process.
- **Verifier:** Read ui/ui.go directly. Line 268 confirmed verbatim: `if idx := m.offset + (msg.Y - 2); msg.Y >= 2 && idx >= 0 && idx < len(m.view) {`. This bounds idx only by len(m.view), not by the actually-rendered range. tableView() (lines 477-481) computes `end := m.offset + rows; if end > len(m.view) { end = len(m.view) }` and only renders rows [m.offset, end) -- confirming the finding's claim about what `end` represents. clamp() (lines 284-304) does not reject out-of-render clicks; it only bounds cursor to [0, len(view)-1] then shifts m.offset to scroll the newly-selected cursor into view -- it does not prevent selecting a row that was off-screen at click time.

Concrete trigger: m.offset=0, len(m.view)=20, listHeight() small (e.g. 2-3 for a short terminal, since listHeight = m.h-2-1-detailHeight-1 with detailHeight=9, floored at 3). A left-click at msg.Y=7 (blank space below the few rendered rows, before the detail pane) computes idx = 0 + (7-2) = 5. Since 5 < 20, the check passes and m.cursor is set to 5 -- a row that was never drawn (only rows 0..listHeight()-1 were rendered at Y=2..2+listHeight()-1). This silently selects/scrolls to a row the user never clicked on, and a subsequent 'x'/'s' keypress would act on that wrong row. The fix suggested (bound idx by min(m.offset+m.listHeight(), len(m.view)), matching tableView's `end`) is correct and directly closes the gap.

This is a real, unguarded off-by-range bug matching the exact mechanism and line described in the finding.

(ui/ui.go lines 83-86). The finding's trigger ("lsof occasionally emits a malformed/protocol-prefixed name string... for a PID matched by -iTCP -sTCP:LISTEN") is speculative and contradicts lsof's documented/observed output format for this exact invocation; a live `lsof -nP -iTCP -sTCP:LISTEN -FpcnPT` run on this machine shows only well-formed host:port strings.
