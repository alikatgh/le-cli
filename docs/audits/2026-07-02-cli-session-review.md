### 1. [HIGH] resolvePath()/withinDir() never handle relative --dir values, so `le stop --dir .` (and any relative path) matches zero listeners even when matches exist
- **File:** `le-cli/cmd/cmd.go` line 327 (finder: path-matching)
- **Verdict:** CONFIRMED
- **Failure scenario:** User runs `le stop --dir .` from inside a project directory to sweep all listeners started there. matchDir(rows, ".") calls resolvePath(".") which calls filepath.EvalSymlinks("."); EvalSymlinks resolves symlink components but does NOT absolutize a relative path, so it returns the relative string "." unchanged. withinDir then compares filepath.Clean(".") == "." against filepath.Clean(r.Cwd), which is always an absolute path (populated from ps/lsof). A relative cleaned path can never equal or be a separator-anchored prefix of an absolute cleaned path, so withinDir returns false for every row. runStopDir then reports "no listeners have a working directory under ." even though listeners are actually running under the current directory — the single most natural invocation of --dir silently does nothing.
- **Verifier:** Verified by reading /Users/s_avelova/Documents/Codex/2026-05-24/le-cli/cmd/cmd.go (note: the finding cited a nonexistent path `le-cli/le-cli/cmd/cmd.go`; the real file is `le-cli/cmd/cmd.go`, same line numbers apply).

The mechanism is exactly as claimed:
- `matchDir` (line 313-322) calls `resolvePath(dir)` (line 314) to get `target`, and `resolvePath(r.Cwd)` (line 317) for each row.
- `resolvePath` (line 327-335) calls `filepath.EvalSymlinks(p)`; I verified empirically with a standalone Go program that `filepath.EvalSymlinks(".")` returns `"."` unchanged (does not absolutize).
- `r.Cwd` is populated by `scan.readCwd` (scan/scan.go:227-249) via `lsof -a -d cwd -p <pids> -Fpn`, which always yields absolute paths — confirmed lsof's `-Fpn` cwd field is absolute.
- `withinDir` (line 339-349) does `filepath.Clean(cwd) == filepath.Clean(dir)` or a separator-anchored prefix check. I ran a concrete simulation: with cwd resolved to `/private/tmp/le-test-dir` and dir resolved to `.` (from `resolvePath(".")`), `withinDir` returns `false`.
- There is no `filepath.Abs()` call anywhere in the repository (`grep -rn "filepath.Abs"` across le-cli returned nothing), and the `--dir` flag (cmd.go:145) is passed straight from cobra's StringVarP into `runStopDir(dir, ...)` → `matchDir(rows, dir)` with no normalization.
- Existing tests (cmd_test.go around lines 230-256) only exercise `withinDir`/`matchDir` with already-absolute paths like `/proj`; no test covers a relative `--dir` value, confirming the gap is untested and unguarded.

Concrete failure scenario: user runs `le stop --dir .` while cwd'd into `/private/tmp/le-test-dir`, and a listener is running with `Cwd == "/private/tmp/le-test-dir"` (as reported by lsof). `resolvePath(".")` returns `"."`, `resolvePath("/private/tmp/le-test-dir")` returns the same absolute path, and `withinDir("/private/tmp/le-test-dir", ".")` returns `false` because `"."` is neither equal to nor a separator-anchored prefix of the absolute cwd. `runStopDir` (line 287-298) then hits `len(matched) == 0` and returns the error "no listeners have a working directory under ." (line 291) even though a listener is genuinely running there. Any relative `--dir` argument (`.`, `./sub`, `..`, `foo/bar`) triggers the same failure, making the single most natural invocation of `--dir` silently useless.

### 2. [HIGH] parsePSUserLines hardcodes lstart as exactly 5 whitespace tokens (fields[1:6]), but ps lstart uses strftime %c which is locale-dependent (LC_TIME/LANG) and can produce a different token count — e.g. ru_RU renders 'среда, 24 июня 2026 г. 10:38:46' (6 tokens, and the time-of-day is the LAST token, not embedded before the year).
- **File:** `le-cli/scan/scan.go` line 190 (finder: recycle-guard)
- **Verdict:** CONFIRMED
- **Failure scenario:** With LC_TIME=ru_RU.UTF-8 (or any locale whose %c rendering isn't exactly 5 space-separated tokens), fields[1:6] silently grabs the wrong slice: r.start becomes 'среда, 24 июня 2026 г.' (missing the time-of-day, which instead gets prepended into r.user). scan.go's captured Listener.StartTime is therefore a truncated/wrong string. Later, kill.go's stillSame() re-reads the FULL, untruncated lstart via `ps -p <pid> -o lstart=` and compares via normalizeWS — which only collapses whitespace, it does not fix the field-boundary mismatch. normalizeWS(fullString) != normalizeWS(truncatedString) for the same still-alive process, so every `le stop` on that PID is refused with 'pid is gone or was recycled' even though the PID is unchanged. This reintroduces the same class of bug the normalizeWS fix targeted, just triggered by locale instead of day-of-month padding, and is a total false-positive (denial of stop) for any locale with a differently-shaped lstart, not a narrow edge case.
- **Verifier:** Verified by reading scan/scan.go and kill/kill.go plus reproducing the mechanism live. parsePSUserLines (scan.go:190-199) hardcodes ps lstart as exactly fields[1:6] (5 tokens). ps lstart is locale-sensitive on macOS/BSD ps; confirmed live that `LANG=ru_RU.UTF-8 LC_TIME=ru_RU.UTF-8 ps -p 1 -o lstart=` outputs 'среда, 24 июня 2026 г. 10:38:46' (6 whitespace tokens, time-of-day last, not tokens 4-5). Simulating parsePSUserLines against a line built from this real ru_RU ps output shows fields[1:6] = 'среда, 24 июня 2026 г.' (time-of-day truncated off) and fields[6:] = '10:38:46 root' (time-of-day incorrectly merged into the user field) — matching the claim exactly. No exec.Command call in scan.go or kill.go sets .Env, so LANG/LC_TIME is inherited unmodified from the caller's environment; grep for LC_ALL/LC_TIME/.Env across the repo found no sanitization anywhere. In kill.go, stillSame() (lines 97-109) re-reads a FRESH, full-length lstart via `ps -p <pid> -o lstart=` and compares it to the truncated scan-time value using normalizeWS, which only collapses whitespace (lines 121-123) and does not repair the field-boundary mismatch. Simulated: normalizeWS('среда, 24 июня 2026 г.') != normalizeWS('среда, 24 июня 2026 г. 10:38:46') — confirmed false. This causes Stop() (kill.go:37-39) to falsely report 'pid is gone or was recycled' for a still-alive, non-recycled process whenever the ps subprocess environment has a locale whose lstart rendering isn't exactly 5 space-separated tokens (e.g. ru_RU.UTF-8), a real and non-narrow trigger condition.

### 3. [HIGH] waitUntil always times out when timeout < pollEvery (400ms), regardless of how quickly the condition becomes true
- **File:** `tools/tools.go` line 97 (finder: timeout-wait)
- **Verdict:** CONFIRMED
- **Failure scenario:** waitUntil polls cond() only on ticker ticks (every pollEvery=400ms via time.NewTicker), never immediately on entry. If a caller passes --timeout shorter than 400ms (e.g. `le wait 5432 -t 200ms` or `le ready 8080 -t 100ms`), the deadline channel (time.After(timeout)) always fires before the ticker's first tick at t=400ms, so cond() is never evaluated even once before waitUntil returns false. Verified by direct reproduction: with timeout=50ms/100ms/399ms and the condition becoming true at t=1ms, waitUntil still reports timeout every time (result=false), while timeout=400ms/401ms correctly succeeds. This means `le wait <port> -t <duration>` and `le ready <port> -t <duration>` unconditionally fail for any user-supplied timeout under 400ms even when the port frees/starts listening almost instantly — directly contradicting the feature's purpose (bounding a wait so scripts can rely on success within budget, per the commit's own example `le ready 5432 -t 30s || fail`). At exactly timeout==pollEvery (400ms) the outcome becomes a race between two timers scheduled at the same instant, decided by select's pseudo-random tie-break rather than deterministic condition-checking.
- **Verifier:** Confirmed by direct code reading. In tools/tools.go, waitUntil (lines 97-114) creates a ticker with pollEvery=400ms (line 15) and only calls cond() inside the `case <-t.C:` branch (line 107). There is no immediate call to cond() before entering the select loop, and no check of cond() in the `case <-deadline:` branch (lines 110-111) — it unconditionally returns false. When timeout < pollEvery (e.g., a caller-supplied `-t 200ms`), `deadline := time.After(timeout)` (line 102) fires strictly before the ticker's first tick at t=400ms, so the select always picks the deadline case and returns false without ever evaluating cond(), even if the condition became true almost instantly. This is reachable from public API: WaitFree (line 65) and WaitListening (line 80) both pass a user-supplied timeout straight through to waitUntil with no clamping to >= pollEvery. Concrete failure: `le wait 5432 -t 200ms` when port 5432 frees at t=1ms — WaitFree calls waitUntil(Free-check, 200ms); deadline fires at 200ms < first tick at 400ms, so it returns false and WaitFree reports a timeout error despite the port having been free the whole time. At timeout==pollEvery (400ms exactly) the two channels become ready at the same instant, so Go's select tie-break makes the outcome nondeterministic, matching the finding's claim.

### 4. [MEDIUM] withinDir's separator-anchored prefix check breaks for dir="/": `d + separator` becomes "//", which no normally-cleaned absolute path is a prefix of
- **File:** `le-cli/cmd/cmd.go` line 339 (finder: path-matching)
- **Verdict:** CONFIRMED
- **Failure scenario:** User runs `le stop --dir /` intending to match every listener on the machine (or simply passes a root-anchored path by mistake). resolvePath("/") returns "/". In withinDir, d := filepath.Clean("/") is "/", and the fallback check is strings.HasPrefix(c, d+string(filepath.Separator)) i.e. strings.HasPrefix(c, "//"). Any real listener cwd like /Users/foo/project cleans to a single-leading-slash path and never starts with "//", so the prefix branch never matches; only the c==d exact-match branch can succeed, requiring a listener whose cwd is literally "/". Every listener under root (i.e. all of them) fails to match, and runStopDir reports none found — silently wrong for a boundary value that's easy to construct (e.g. a misconfigured script passing an empty path that gets joined into "/").
- **Verifier:** Verified by reading cmd.go and by actually executing the withinDir/resolvePath logic in a standalone Go program. le-cli/cmd/cmd.go:339-349:

```go
func withinDir(cwd, dir string) bool {
	if cwd == "" || dir == "" {
		return false
	}
	c := filepath.Clean(cwd)
	d := filepath.Clean(dir)
	if c == d {
		return true
	}
	return strings.HasPrefix(c, d+string(filepath.Separator))
}
```

Concrete trigger: `le stop --dir /`. The `dir` flag flows unmodified from stopCmd (cmd.go:133-137) into `runStopDir` → `matchDir` (cmd.go:313-322) → `resolvePath("/")`, which resolves via `filepath.EvalSymlinks("/")` to `"/"` (verified: prints `"/"`). In `withinDir`, `d := filepath.Clean("/")` is `"/"`, so the fallback branch is `strings.HasPrefix(c, "/"+"/")` = `strings.HasPrefix(c, "//")`. For any real listener cwd like `/Users/foo/project` (cleaned to a single leading slash), this is false — confirmed by running the exact function: `withinDir("/Users/foo/project", "/")` returns `false`, while only `withinDir("/", "/")` returns `true` via the `c == d` exact-match branch. There is no special-casing of root anywhere in cmd.go, and no normalization of the `--dir` flag before it reaches this path. So `le stop --dir /`, a directly reachable ordinary CLI invocation, silently matches zero listeners instead of "every listener on the machine" as a user would reasonably expect from a root path.

### 5. [MEDIUM] sameExe's fallback (used when l.StartTime is empty) only compares argv[0]'s basename, so a PID recycled to a different process that happens to share the same interpreter/binary name (node, python, java, etc.) is falsely treated as 'still same' and Stop proceeds to signal/stop the wrong process.
- **File:** `le-cli/kill/kill.go` line 125 (finder: recycle-guard)
- **Verdict:** CONFIRMED
- **Failure scenario:** Listener scanned with CommandLine '/usr/local/bin/node server.js --port 3000' but StartTime empty (reachable whenever dropPartialRows drops the ps-lstart/user row for that PID, e.g. due to the locale token-count bug above, or a transient one-of-two-concurrent-ps-calls failure — in which case Scan() also falls back CommandLine to lsof's short name via `if l.CommandLine == "" { l.CommandLine = a.command }`, making the comparison even coarser). If that PID is later recycled by the OS to an unrelated 'node other-project/other-app.js' process before `le stop` runs, stillSame()'s sameExe() only compares 'node' == 'node' and returns true, defeating the PID-recycle guard entirely and causing the wrong process to receive SIGTERM (or brew/docker stop, though those have their own re-verify).
- **Verifier:** Verified by reading /Users/s_avelova/Documents/Codex/2026-05-24/le-cli/kill/kill.go (note: the file lives at le-cli/kill/kill.go, not le-cli/le-cli/kill/kill.go as the finding's path states — the doubled segment is a typo, but the line content matches exactly) and the sibling scan/scan.go.

stillSame (kill.go:97-117) only takes the strong lstart-based path when l.StartTime != "" (line 98). When StartTime is empty, it falls to line 111-116: `out, err := runOutput("ps", "-ww", "-p", ..., "-o", "command=")` then `return cur != "" && sameExe(cur, l.CommandLine)`. sameExe itself (line 125-127) is:
```go
func sameExe(a, b string) bool {
	return argv0Base(a) == argv0Base(b)

```
which reduces to comparing only `filepath.Base(fields[0])` of each command string (line 129-135) — i.e., just the executable basename (e.g. "node"), ignoring the rest of argv entirely. No PID start-time, inode, or full-argv check backs this fallback, and nothing else in Stop() re-verifies before termProcess(l.PID) is called in the default branch (line 76-79) — the existing kill_test.go even encodes this coarseness explicitly: `{"/usr/bin/node", "/usr/local/bin/node", true}` treats two distinct node binaries at different paths as "same."

The claimed reachability path is also confirmed in scan/scan.go: Scan() falls CommandLine back to lsof's short name at line 111-114 (`l.CommandLine = psInfo[pid].command; if l.CommandLine == "" { l.CommandLine = a.command }`), and dropPartialRows (scan.go:178-184) drops a psInfo row entirely (not just the missing field) whenever the two concurrent `ps` calls disagree on whether they saw the PID (`seenUser[pid] != seenCommand[pid]`), leaving StartTime empty for that Listener while CommandLine still gets lsof's coarse short name via the Scan()-level fallback. So a Listener with StartTime=="" and a real-looking CommandLine (or just lsof's short command name) is a genuinely reachable state, not a hypothetical.

Concrete failure: Listener scanned with StartTime=="" (via the above path) and CommandLine containing "node" as argv[0]'s basename. Before `le stop` runs, the OS recycles that PID to an unrelated process also invoked as some node binary (e.g. `/usr/local/bin/node other-project/other-app.js`). stillSame() takes the fallback branch, sameExe("... /usr/local/bin/node other-project/other-app.js", l.CommandLine) compares "node" == "node" → true → stillSame returns true → Stop()'s default case sends SIGTERM (kill.go:76-79) to the wrong, unrelated process. The mechanism, the reachability of the empty-StartTime state, and the lack of any secondary guard are all confirmed by direct code reading, not speculation.

## Refuted candidates (for the record)

- [recycle-guard] The same locale-dependent lstart token count can also make a valid ps line fail the `len(fields) < 7` guard, causing parsePSUserLines to never mark that PID as 'seen', which makes dropPartialRows delete the row entirely and silently drops the listener from Scan() results (or forces it onto the weaker basename-only stillSame fallback if it survives via lsof's short-name fallback). — The locale-dependent mechanism is real: reproduced live with `LC_TIME=ja_JP.UTF-8 ps -ww -p 1 -o pid=,lstart=,user=` giving `1 水  6/24 10:38:46 2026 root` = 6 whitespace fields, failing `len(fields) < 7` in scan.go:190, so parsePSUserLines never marks that PID `seen`, and dropPartialRows (scan.go:178-184) deletes it from the internal `rows` map because seenUser[pid] != seenCommand[pid].

But the finding's claimed consequence is false. Scan() (scan.go:99-115) builds its `listeners` slice by iterating `order`, the PID list derived from lsof output, NOT from `rows`/`psInfo`. `psInfo[pid]` on a deleted/missing key is a Go map lookup that returns the zero-value `psRow{}` (empty strings), not an omission. So the listener is NOT deleted from Scan()'s output — it still appears with `Command` from lsof, empty `User`/`StartTime`, and `CommandLine` falling back to lsof's short name (scan.go:111-114, the explicit `if l.CommandLine == ""` fallback). Neither cmd/cmd.go nor ui/ui.go filters listeners on empty `User` or `StartTime` (grep confirms zero such usages), so the listener is not hidden from `le scan`/`le list`.

The only real effect is that kill.go's `stillSame` (kill.go:97-116) falls back to the weaker basename-only comparison when `StartTime == ""` — exactly the documented, intended fallback the `dropPartialRows` comment (scan.go:161-170) already describes for "a PID readPS has no data for at all." The finding itself hedges with this same alternative ("or forces it onto the weaker basename-only stillSame fallback"), but asserts the stronger "silently drops the listener from Scan() results" as the primary claim, which is refuted by tracing the actual map-lookup/iteration logic.
- [concurrency-di] runCmd (and by the same pattern kill.go's runCombined/runOutput/termProcess and intel.go's DockerContainerID/BrewServiceKnown) is a plain, unsynchronized package-level var used as the DI seam, but scan.go's own comment admits it 'invokes this from two goroutines at once' — there is no mutex/atomic guarding the var, only a code-comment convention that callers/tests must never reassign it concurrently with a read. — The mechanism described is real in the abstract (Go's race detector would flag a concurrent write to the unsynchronized package-level `runCmd` var racing with a read), but it does not describe an actual bug in scan.go as it exists. Concurrent *reads* of `runCmd` from the two goroutines spawned in readPS (scan.go:150-151) are not a data race in Go — only a concurrent write would be. No code path in scan.go, kill.go, or intel.go reassigns these vars outside of test files, and the only place they are reassigned in tests (scan_di_test.go's `stubRunCmd`, line 14) does so synchronously before calling `Scan()` and restores it via `defer` after the call returns — never concurrently. Grepping the entire le-cli repo for `t.Parallel` returns zero hits, and `go test -race -count=1 ./scan/...` passes cleanly with no race reported. The finding itself concedes: 'This is unreachable in the shipped binary (production never reassigns the var after init)' and hedges its trigger as merely 'a live hazard for any test using t.Parallel() ... a very natural way to write tests' — i.e., a hypothetical about tests that don't exist, not a demonstrated defect in the actual code at scan.go:31 or anywhere else in the reviewed file. There are no concrete inputs/state in the current codebase that trigger a real wrong result, crash, or detected race.
- [concurrency-di] readPS's inline comment asserts the shared `rows` map is 'written only sequentially, never at once' — true as written, but this safety is an unenforced invariant resting entirely on `parsePSUserLines`/`parsePSCommandLines` being called strictly after `wg.Wait()`; nothing in the function signature or types prevents a future edit from moving one of those calls before the Wait or into a goroutine. — The candidate finding itself concedes "Current code is correct" — it is not describing a present bug but a hypothetical future refactor risk. Tracing scan/scan.go lines 142-158: the two goroutines (lines 150-151) write only to local string vars out1/out2, never touching `rows`. wg.Wait() at line 152 fully synchronizes before rows is touched at all. Then parsePSUserLines(out1, rows) at line 155 and parsePSCommandLines(out2, rows) at line 156 run sequentially on the same (main) goroutine — ordinary sequential Go statement execution, not concurrent goroutines — so there is no possible interleaving today. No concrete input or state in the current code causes a concurrent write to `rows`; the claim requires imagining a future edit that doesn't exist. This fails the bar for CONFIRMED/PLAUSIBLE, which require a demonstrable defect in the code as written, not speculation about what a hypothetical future refactor might introduce. Flagging "the invariant is only a comment, not type-enforced" is a valid code-maintainability/robustness observation in principle, but as a concurrency-bug finding about this file it is REFUTED — the code is correct and the mechanism has no live trigger.
